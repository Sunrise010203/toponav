  最终控制器却仍为`moving`，拒绝发生的那张输入及已产生的决策/命令未写入日志。
- 修改前时序剖析运行`profile-C02`同样遇到租约到期。该次`step`最大耗时约1.447墙钟秒，
  几何约0.019秒、模型约0.232秒。它说明慢步进是本次观测到的因素，**不能据此声称几何算法是根因**。
  未以算法优化、增加线程、延长0.8秒租约或重置失败门禁来掩盖这一问题。

两次原始失败、原始RGB/日志/冻结清单和剖析结果均保留。

## 修改内容

仅修改`simulation/gazebo_cross_validation.py`的异常处理与留存顺序：

1. 主相机帧在控制器/门禁/命令提交之前保存，并记录待处理tick的身份、原时间与像素SHA256。
2. 保留已经生成的原控制决策、适配后的线协议命令、门禁拒绝原因、门禁输出零速及失败阶段。
   后端未返回时`decision=null`，不伪造决策。
3. 外层异常先锁存门禁并请求零速，再取消活动控制器，再写失败工件/执行原清理。
   零速提交失败另行记录，原始异常不被它替换；**软件终态不等于执行器已经停下**。
4. 正常决策在可选显示之前提交到JSONL；显示异常不能丢掉已提交过的那一条命令。
   新`audit/failure.json`和结果中的`failure_record`单独保留失败尝试，不把它伪装成成功决策、
   也不回写原决策前缀。无外层异常的正常拒绝/完成路径不增加该失败工件。

`zero_command_submitted`仅表示传输调用未抛异常，不是底盘反馈或制动保证。
如果取消自身失败，`cancellation_error`及`controller_terminal`如实记录，不宣称已锁存。
正常`visual_stop`/已中止的锁存语义不改；不引入失败后重启或恢复运动。
