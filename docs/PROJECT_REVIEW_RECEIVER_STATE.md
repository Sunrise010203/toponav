## 已复现的问题

1. 原校验只检查字段类型、单调时钟/序号与锁存标志，未检查字段之间是否符合原生租约状态机。
   “disarmed但命令序号为正”“accepted但期限已过”“同一命令序号的期限/速度改变”可被保留为有效审计。
   锁存后增加序号且保留remote_stop，也未被标记为错误。
2. 公共JSON解码器会对深度嵌套消息抛出`RecursionError`；原接收回调未捕获它，也未写入粘性审计错误。
   本地反例中异常逸出后，先前有效状态仍可通过`require_ready`。不据此推断所有原生绑定都采取相同异常退出行为。

`probe_state.py`保留修改前后同一输入的结果；`baseline-nested-status.json`保留未捕获的异常及原错误状态。

修改前的**真实原生状态话题**诊断，在L型世界运动后发布一条本会话、合法字段/类型但不可能出现的状态：
保持实际正命令序号和期限，却声称disarmed/零速度。实际`GazeboIO.receiver_status`回调确认收到，
旧校验将其加入有效事件，最后任务仍`completed=true`。这是**反馈审计未拒绝不一致数据**的反例，
不是原生租约被绕过、未停稳或发生物理碰撞的证明。

## 修改

- 未授权状态必须为序号0、期限0、零速度；序号0不能带租约，正序号不能缺少期限。
- accepted必须为正序号，且发布时墙钟严格早于期限，期限不超过该发布时刻+原0.8秒。
  使用的是**状态内的发布时刻**，不是收到状态的时刻；不新增心跳或从收包时刻续租。
- 到期状态必须有实际命令序号，并已到其期限；序号不得超过原生uint64范围。
- 同序号的绝对期限不得改变，未锁存时的授权速度不得改变；锁存后序号、期限和原故障原因都不能改写。
- 可允许状态话题漏掉中间序号、不同新命令改变速度/期限，以及stop在没有首条运动命令时直接锁存。
  不强求每条状态连续到达，不给正常故障/停车链增加新的运动权限。
- 深度嵌套JSON的`RecursionError`进入原粘性错误路径，不从回调逸出。后续合法状态不能清除先前错误。
- 原`require_ready`及完成判定沿用该粘性错误：后续非零命令被拒绝，零速停车仍可提交；
  最终即使有新鲜零速/停稳证据，也不能将存在坏反馈的任务记为完成。

错误记录本身**不会在回调线程发布速度**，不新增第二个生产发布者或异步停车承诺。
停车仍由下一次执行/失败清理以及既有独立原生绝对租约完成。
