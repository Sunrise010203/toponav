- 固定`MAX_RECEIVER_SUBMISSIONS=16384`，只在原生产严格模式`require_frame_echo=True`自动启用，无CLI/环境放宽开关。
  独立预算大于2200 tick任务及8192候选预算，为控制请求留出记录空间；不增加原生4096个已接受帧上限。
- 前16384条继续完整复制并执行原会话、字段、请求顺序、时钟、序号及绝对期限校验；最后名额可正常使用，不提前产生容量故障。
  满后下一次发送观察回调在复制/校验前锁存容量故障；保留完整有效前缀，不淘汰、不覆写、不清空后继续运行。
- 超限的观察回调直接返回，不解码/复制原始输入，不推进保留序号或终止状态，不增加或重建候选。
  其内容和时间没有经过接收证据校验，不能声称是合法发送、原生拒绝、已接受命令或新鲜反馈。
  无效或巨大输入在超限后也只属于未校验回调，不冒充原校验通过。
- `_submission_not_retained`在`2**64-1`饱和，达到后明确标记只为下界，不让该诊断计数器本身无限增长。
  较早错误优先保留，正确反馈、STOP及后续零请求不能清除故障。
- 此观察者在socket send之后执行。容量故障不抛错，不关闭原本健康的执行通道，零请求、ACK与原10次停车清理继续走原路径。
  原执行器、每请求ACK校验及原生联锁不受容量分支免检；坏ACK仍不可恢复关闭通道。
  触发容量故障的那次发送不能被追溯撤回；之后原`require_ready/fresh`拒绝非零运动和任务完成。
- 超限后终态不再声明`final_authority_bound`或`frame_echo_verified`，即使反馈恰好对应保留前缀中的候选。
  旧候选仍可作结构审计，遗漏候选反馈依旧被拒；不会用后来的零状态伪装完整发送绑定。
- 严格摘要新增`submission_history`：固定上限、留存数、耗尽标志、未留存的未校验回调计数及下界标识。

  runner仍写出`audit/receiver-submissions.json`完整前缀，摘要披露不完整性，不伪造遗漏记录。
