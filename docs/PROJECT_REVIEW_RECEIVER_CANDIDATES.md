## 问题与策略

接收状态列表已有限制，但每次实际发送非终止命令仍向候选映射新增一项。
候选代表“已发送”，不代表原生已经接受；既可能没有状态反馈，也可能被原生拒绝，不能用原生4096项已接受帧上限来声称Python映射已有限制。
修改前实际严格记录器连续记录8193份合法合成发送元数据，保存8193项候选且无容量故障；这是存储边界反例，不是原生授权、RGB采集或RSS测量。

- 固定`MAX_RECEIVER_CANDIDATES=8192`，生产原有`require_frame_echo=True`路径自动启用，无新CLI/环境放宽开关。
  这是Python发送候选的独立预算，大于2200 tick任务预算，并给原生4096项预算之外的未确认/被拒发送留出空间；不是将原生可接受数量升级为8192。
- 最后一个名额仍可记录，不提前故障。下一份合法非终止命令已经send后，锁存候选容量故障并停止增加映射。
  保留完整前缀，不滚动淘汰、不覆写、不清空或从未限制的发送列表重建遗漏候选。
- 发送后观察者不因这个容量故障抛异常、关闭本来健康的执行通道。
  实际发送副本仍按原校验记录，序号/请求顺序继续推进；非终止零命令也不让映射突破上限。
  终止命令、idle/stop/shutdown本来不产生候选，仍走原记录路径。
- 原会话、字段、序号、时钟、期限及终止校验均保留；坏记录依旧抛出原异常，不因达到容量而免检。
  较早错误不被覆盖，后来的正确accepted/STOP不能清除故障。
- 原`require_ready/fresh`通过粘性错误拒绝后续非零命令；本批不是发送前的全局内存/计时保证。
  容量是在send后识别，触发它的那次发送不能被追溯撤回，仍受原执行器/原生0.8秒租约和4096帧上限约束。
- 超限后即使最后留存反馈对应最后留存候选，也不再声明`final_authority_bound`或`frame_echo_verified`。
  遗漏候选的反馈继续按原绑定校验拒绝；保留下来的旧反馈可以进入结构审计，但不能洗掉任务失败或认证最新发送。
- 严格模式摘要新增`candidate_history`，披露上限、留存数、耗尽标志和范围。
  历史/离线兼容模式保持原行为，不称其有界。
