## 复现与边界

原`ReceiverEvidence.require_ready()`只检查解析错误、已有状态和锁存标志，未检查发布时间与当前期限。
修改前的真实原生诊断在第三次非零提交后丢弃接收回调；60 tick内仍有29次基于超过0.8秒旧状态的非零提交。
独立执行器仍正常续接新命令，因此不能把执行器自身的命令租约等同于接收反馈持续可用性检查。
这是反馈门控缺口，不是已经复现物理失控；原生绝对租约、执行器和最后轮命令联锁始终保留。

首次30 tick诊断在最后一次非零提交时尚未跨过时效边界，脚本断言失败；原日志和会话保留。
随后只把该工程诊断延长至60 tick，未改变生产租约、速度、场景或相机。
另有真实适配器单测先证实陈旧disarmed状态原来不会阻止首次非零提交，再修改生产代码。

## 最小运行门控

新增`ReceiverEvidence.require_fresh(now_steady_s)`，实际`GazeboIO.command()`的所有非零轴在条件锁内调用：

- 保留原结构/粘性错误/锁存检查。
- 要求当前同主机monotonic时刻有限、非负且不早于上次成功门控时刻。
- 仅按原生状态内的`wall_s`计算年龄，要求`0 <= now-wall_s < 0.8`；到达边界即拒绝，未来状态也拒绝。
- accepted状态还必须满足`now < deadline_steady_s`。新发布的状态也不能延长原绝对命令期限。
- 时效、时钟或就绪失败写入原粘性`error`；后来合法命令或零状态不能把失败清掉。保留原状态历史，不重写期限。
- 失败发生在执行器非零请求之前，并消耗当前绑定上下文；由原runner异常路径保存失败tick、请求零、取消任务、清理。
- stop、idle和绑定零命令不经过新门控，缺反馈或坏时钟不能阻碍停车请求。

无参数`require_ready()`仍是历史/离线结构检查，不新增壁钟依赖；它不是运行授权接口。
生产非零路径不能以它代替`require_fresh()`。本批没有新增线程式周期看门狗、速度发布者、通道重连或授权重试。

## GUI等待启动的兼容处理

原生暂停世界在物理时间和授权都不变化时不周期发布状态；长时间等待“开始”后旧disarmed状态也必须拒绝直接发运动命令。
GUI route/vision分支在收到显式开始请求后、进入首个导航tick前，调用一次`refresh_disarmed_receiver()`：

1. 原结构校验必须通过，且原生状态和独立客户端最后有效ACK均为未锁存、disarmed、序号0、零速度。
2. 只有这种从未授权任何命令的初始状态，才做一次原规格12步物理观察和0.1秒等待，然后执行同一严格新鲜度门控。
3. 无新鲜反馈、未来反馈、锁存、解析错误或未知步进结果都失败退出；不重试步进，不重置错误，不发送任何速度/租约请求。
4. 已接受过命令或用过的会话不允许进入此初始化路径；运动中的陈旧反馈仍立即走失败停车，不能用初始化恢复。

单测覆盖实际GUI等待分支与真实门控方法。原生parked诊断在未授权状态等待1秒后，调用这一个生产初始化方法再运行受限L样例；
它不是GUI视觉自动化测试，也没有测试专用物理步进循环。该额外启动观察明确记录在`startup.json`中。
