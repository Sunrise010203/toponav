## 已确认的缺口

上一批已能在坏ACK后粘性关闭客户端，独立执行器/原生联锁依靠原EOF/绝对租约停车。
但生产finally把零请求和后续10次观察步进放在同一try内：通道关闭导致零请求失败时，观察也被跳过。
因此原cleanup.steps_completed=0、audit.stationary=false，缺少独立的失败后物理观察；不能仅凭软件锁存宣称停稳。

本批修改前的真实原生诊断再次注入一条命令序号不一致的ACK：任务正确aborted、completed=false，
但生产未进行失败后观察。**没有使用上一批的补充物理步进测试hook**，未伪造姿态/图像或声称已有停车证明。
旧版结果及修改前源码快照保留；这是观察缺口，不是已复现物理失控的结论。

## 修改

只在零请求失败、未取得零ACK且客户端已failed时，尝试独立观察；不改变原正常清理路径。
独立结果存为`independent_stop_observation`及`audit/independent-stop.json`，不覆盖原cleanup或主审计字段。

观察必须同时满足：

1. 客户端确实不可恢复失败、本地socket已关闭，保留最后一条已校验命令序号；不重新连接、不重试请求。
2. 步进helper仍存活且无粘性失败/未知完成结果。之前步进失败则不再排队；本路径任何一步失败即结束，也不重置helper失败标志。
3. 在原0.8秒预算内等到本会话已有校验器接收的锁存零状态，其序号不落后于最后有效ACK，发布时刻不超前且龄小于0.8秒。
   使用状态内的同主机monotonic发布时刻，不把收包或等待时间当成续租；解析错误不能被后来合法零状态清除。
4. 确认零授权后，才使用原清理的10次步进预算（每次12个物理步，沿用0.03秒观察间隔）。每次开始前及结束时都重新检查状态/步进helper。
   不延长原命令期限、不恢复控制器更新、不发送任何新速度命令。
5. 最后一个观察步必须实际新增至少两条有限、有序、非未来的姿态，且原生零状态也属于该最终步。
   按原0.01m/s与0.02rad/s严格小于门槛测量静止；收到步进ACK、旧姿态或单条姿态都不等于停稳。

`observation_complete`只表示获得了合格观察，`stationary`另按物理速度判断；仍运动时可完整观察但stationary=false。
已真实锁存的到期/坏包等故障零状态可以被观察，但其故障原因不被清除，也不因此获得导航成功或重新授权。
