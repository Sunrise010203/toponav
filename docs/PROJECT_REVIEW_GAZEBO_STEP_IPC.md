# 第十二批：Gazebo步进助手有界通信

日期：2026-10-29开始，2026-10-30续跑最终验证。本批是执行器通信与异常退出修复，**不是导航完成或实时停车验收**。

## 问题与复现

原生服务调用放在独立助手进程，避免Gazebo Transport绑定占用主进程GIL、饿死图像回调。
但主进程在助手启动及每次步进时使用无期限`stdout.readline()`：

- 助手卡住、不输出换行或只输出半行时，主流程无法到达后面的“物理时钟推进30秒”超时检查。
- 发生响应/时钟错误后没有独立通信失败锁存；继续清理步进可能再次发送请求，
  将旧请求的迟到ACK误当作新请求回复，或在完成状态未知时继续排队物理步进。
- 握手未完成时`GazeboIO`构造尚未返回，`run().io`仍为None，原收尾无法回收已启动的助手。
- 原`ok`检查接纳非空字符串或数字1，EOF/非对象JSON则落入不明确的解析/属性错误。
- 助手已退出时，写管道的flush失败会留下缓冲字节；原收尾再次关闭管道时重复flush，
  再次抛BrokenPipeError，可能遮蔽已捕获的原异常并阻止保存最终结果。

新增测试使用**真实OS管道和合成Python助手**，不是模拟`readline`返回值。
延迟/半行助手在0.4秒后才输出整行：旧代码无视测试的0.08秒通信预算并继续，
新代码在预算到期时报错。最终16项对原runner均失败，但其中新接口/状态字段缺失不算新增故障；
正向测试仍失败于新字段缺失，也不能称旧有效通信本来就坏。

初次基线的迟到ACK用例还等满了原30秒物理时钟等待；为使复现聚焦通信锁存，
最终夹具补上第二次时钟推进并为非超时用例放宽测试通信预算到1秒（生产预算不变）。
原始15项阶段日志保留；补充管道关闭反例后的最终16项针对哈希核对的原runner仅在内存加载，
仍16失败，未回滚生产源码。

## 最小修复

仅修改`simulation/gazebo_cross_validation.py`：

1. `StepServiceClient`用selector等待管道可读，配合原始字节读取及自身行缓冲，不对半行调用阻塞`readline`。
   握手与请求回复各有**新增30秒通信上限**；正常请求仍由原助手执行，原生请求超时15秒不变。
   原物理时钟推进等待仍单独30秒，不把ACK当作物理完成。因此两阶段等待理论上可累计约60秒，
   这不是30秒端到端完成承诺，更不是运动租约。
2. 明确拒绝EOF、坏JSON、非对象和非内建True的`ready`/`ok`。
   只允许原助手已有的整数1—120步预算；每次只发送一个小请求并等待回复。
3. 通信异常、取消或已ACK但物理时钟未推进时锁存失败；后续请求立即拒绝，
   不消费迟到回复，不重新启动助手，不恢复运动，也不再追加清理物理步进。
   零速提交独立于步进助手，仍走原异常停车链。
4. `start_step_service`在握手失败时杀死并回收**自己刚创建的助手**，再传播原异常；
   不终止其他用户进程。正常运行仍由原收尾管理助手。
5. 请求失败时关闭已失效的写管道；关闭时重复flush产生的次级OSError不覆盖原始失败，
   防止主流程收尾再抛同一BrokenPipeError而丢失结果报告。

没有增加后台步进线程、重试或墙钟看门狗，没有延长0.8秒MotorGate租约。
相机/位姿/接触回调、原生服务实现、步进物理目标和30秒时钟等待、控制器、模型、地图均未改。
`run`与第十一批新鲜停车审计保持AST相同。
