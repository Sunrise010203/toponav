## 已复现的问题

旧runner最终请求零速、再执行10次12迭代清理步进，但异常被直接忽略。
最终静止审计只读全部轨迹的最后两条位姿，未要求它们来自清理后的仿真时刻。
因此，即使最终零速/步进失败，或位姿流停止，旧的静止终点位姿仍可能配合`visual_stop`产生`completed=true`。

新增12项执行契约测试，修改前全部失败。其中5项直接复现了假完成：零速提交失败、
步进失败、旧位姿、最后一步仅一条新位姿、未来位姿；其余失败涉及新增审计字段/显式false，
不是另外7种假完成。重复/逆序时间本已无法证明静止，不把它们误称为新发现。
测试使用合成终态/终点、假物理接口和真实MotorGate，**不能作为真实导航完成证据**。
原始修改前日志和JUnit保留，未回滚生产文件或重写历史证据。

## 最小修复

仅修改`simulation/gazebo_cross_validation.py`的`run`：

- 新`cleanup_stop`及`audit/cleanup-stop.json`保留是否尝试/提交零速、请求和完成步进次数、
  零速前位姿数量与仿真时刻、最后一步开始/最终仿真时刻及清理异常。
- 清理故障使结果不可完成；已有主异常不被清理异常替换。清理单独失败时，结果`exception`明确报告。
  不重写控制器`visual_stop`锁存，不把清理故障伪造为某张控制帧的失败；原`failure_record`只表示外层执行异常。
- 停车证明同时要求零速提交成功、原10步全部完成且无异常、最后两条位姿均为零速请求后新收到的数据，
  并满足`最后清理步开始时刻 < 前一条位姿时间 < 最后一条位姿时间 <= 清理最终时钟`。
  时间比较使用原生纳秒转秒，不添加帧龄宽限；不增加步数/等待时间。
- 新`post_stop_pose_pair_fresh`披露证据新鲜性；无足够位姿时`stationary=false`。
  原速度估计仍可作为诊断出现，但新鲜性不足或清理失败时，估计为0也不能宣布静止。
- 原10×12步、线速度`<0.01m/s`、角速度`<0.02rad/s`、所有几何/节点距离门槛不变。

`zero_command_submitted`仍只代表调用未抛异常，不是硬件接收/执行反馈。
新审计只检查仿真最终区间，不是整条制动曲线、制动距离或独立墙钟看门狗。
原生消息回调、步进同步、相机同步、限速、MotorGate、控制器、模型和地图均未修改。
本批不扩展为数值序列清洗或节点事件最近邻审计重构。
