## 发现与复现

旧`Command`持有与`PreUpdate`共享的互斥锁后，才遍历全部protobuf元数据、将键值复制到map，
最后检查字段数量。其他原生发布者不经过Python发送端的包长限制。

`compare_decoders.py`直接提取旧源码的解析语句，使用同一编译探针，统计**解码阶段**的访问/分配，
不把protobuf形状的测试视图冒充真实传输或物理制动测试。探针先构造消息，再开始计数：

| 输入 | 旧解析器 | 新解析器 |
| --- | --- | --- |
| 65,536个唯一字段 | 读取65,536个键，分配14,745,651字节，最后才拒绝 | 不读取任何键/值，零分配拒绝 |
| 1MiB帧身份 | 分配2,097,956字节；解码后才由租约策略拒绝 | 复制前零分配拒绝 |
| 1MiB键 | 分配1,049,394字节，最后才拒绝 | 仅检查键长，零分配拒绝 |

这是原共享锁内存在输入规模相关开销的确定性反例；**不据此声称旧版一定超出0.8秒或已经发生物理失控**。

## 修改

- 新增生产C++解码器`receiver_envelope.hh`，原生插件直接实例化，测试编译执行相同解码器。
- 首先O(1)检查元数据恰好8项；再检查固定键集合、重复键、每项仅1个值、额外速度轴为零。
- 键最多32字节；version/session/kind/seq/frame/三个数值分别最多1/256/7/20/256/64字节。
  原Python发布格式在范围内；数值仍严格完整解析，拒绝溢出/尾缀。有限值、原期限和权限校验仍由原租约策略负责。
- 先检查全部字段，再复制至多519字节的session/kind/frame内容；不构建输入规模相关的map。
- 解析、字符串分配和异常处理移到共享锁外；锁内仅进行原租约策略更新/拒绝锁存。
  原`Poll`、最终轮速写入、优先级、状态发布和物理审计均不改。
- 新头文件同时进入构建哈希和运行冻结。修改后旧二进制失效，必须匹配源码重建，不静默回退。

## 仍有的边界

这里只限制**protobuf已经解码后、本接收回调执行的应用解析工作**。原生传输反序列化、消息排队/洪泛、
原DiffDrive等其他插件、Gazebo/OS调度和物理引擎仍可能阻塞；不是网络DoS隔离或所有锁均有界的保证，
也不保证接收器自身崩溃/系统挂死时实车制动。实车仍需独立底盘固件/驱动器及物理反馈验收。
